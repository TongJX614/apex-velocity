## 一、域间过渡：三套渐变，各管一件事

九公里的大陆上，如果域与域之间是硬边，开车穿过去就像在翻书。
本轮把过渡拆成三层，**每一层用不同的过渡带长度**——这是关键。

### 1.1 地形（保持现状，不动）

地形用 `_zone_weight(d, radius)`：域中心权重 1，到 `radius × 1.55` 衰减到 0。

地形**必须**保持域的形状——城区要平、雪山要陡、峡谷要深。
如果把地形的过渡带也拉长，城市就会把旁边的雪山压平。

### 1.2 颜色（过渡带 2.6 倍域半径，最长）

`_color_zone_weight(d, radius)`：域中心权重 1，到 `radius × 2.60` 衰减到 0。

相邻域中心距 2450m（正交）/ 3457m（对角），域半径 1150~1250m。
用 1.55 倍半径时，两域的缓冲只有几十米，颜色是硬跳变；
用 2.60 倍半径后，两域的过渡带在中点重叠，
**在中点处两域权重各约 0.5，基色正好混成 50/50**。

实现要点（`open_world.gd` → `_ground_color`）：

```gdscript
# 33 万个顶点上跑，所以必须零分配：直接累加颜色和权重，
# 不建字典、不建数组（早期版本每个顶点建一个 dict 数组，
# 构建时间直接翻了 1.5 倍）。
for i in ZONES.size():
    var w := _color_zone_weight(dist, radius)
    total += w
    acc += ZONE_BASE_COLORS[i] * w
c = acc / total
```

过渡带里的"主导域"如果权重不足 90%，就把 kind 退化成 `wild`——
否则在两条域的边界上，雪线、岩层、坡度露岩会来回闪。

### 1.3 植被（跟着颜色一起渐变）

`_build_transition_vegetation()`：在每对相邻域的中点带，
**同时**种上两边的树种，并且越靠近哪一域就越偏向哪一域的树。

> 雪山隘口 → 冰川湖：开过去看到的是"松林慢慢变成矮林 + 枯木"，
> 而不是松林一刀切断。

### 1.4 光照（过渡带 1.55 倍域半径，最短）

`_zone_weight()` 直接复用**地形**的权重（不另设）。

理由：光照渐变太长会让人晕（开着半天天色不变），
太短又会在域边界上"啪"地一下换掉。1.55 倍域半径 ≈ 1800m，
以 120km/h 算要开 54 秒——足够长到有"天在变"的感觉，又短到不会晕。

## 二、白天 → 黑夜城市 / 白天 → 火山地界

### 2.1 核心：把"夜"从一个布尔值变成连续量 `night01`

每个域的 `stars` 字段天然就是"这个域有多黑"的作者意图：

| 域 | stars | 语义 | night01 |
|---|---|---|---|
| 霓虹都市 | 1.00 | 深夜 | 1.00 |
| 冰川湖 | 0.55 | 极夜 | 0.55 |
| 熔岩盆地 | 0.30 | 火山黄昏 | 0.30 |
| 赤岩峡谷 | 0.12 | 黄昏 | 0.12 |
| 落日港湾 | 0.08 | 落日 | 0.08 |
| 天际环城 | 0.05 | 黄昏未来城 | 0.05 |
| 翡翠海岸 | 0.00 | 正午 | 0.00 |
| 雪山隘口 | 0.00 | 白昼 | 0.00 |

`night01 = Σ(stars_i × w_i)`，`w_i` 是当前位置各域的归一化权重。

**白天 → 黑天城市**：`night01` 从 0.00 连续爬到 1.00。
**白天 → 火山地界**：`night01` 从 0.00 连续爬到 0.30。

### 2.2 night01 驱动了什么

| 参数 | 公式 | 效果 |
|---|---|---|
| 太阳亮度 | `lerp(日 1.9~3.2, 夜 0.9~2.0, night01)` | 太阳连续沉下去 |
| 太阳颜色 | `lerp(暖白 #fff2da, 冷蓝 #cdd8ff, night01)` | 落日红 → 夜蓝 |
| 天空 `night` | `= night01` | 星星逐渐出现 |
| 星星数量 | `stars × night01` | 夜里才满天星 |
| 环境光 | `lerp(天空色, 冷蓝月光, night01)` | 地面从冷暖变冷暗 |
| 车灯 | `night01 > 0.5` 时开 | **黄昏过半自动亮灯** |

> "白天到黑天"因此不是"换个滤镜"，而是一条连续的物理曲线：
> 太阳沉下去 → 星星冒出来 → 地面变冷 → 车灯自己亮。
> 中间那段 `night01 ≈ 0.5` 的黄昏，是最有质感的一段。

### 2.3 主题字段怎么混

`_blend_zone_themes()`（`main.gd`）：

- **颜色**（`skyTop` / `skyHorizon` / `fogColor` / `hemiSky` / `sunColor` …）
  → 逐通道加权插值
- **数值**（`exposure` / `ambientEnergy` / `sunPower` / `fogFar` / `glowOpacity`）
  → 加权平均
- **数组**（`sunDir`）→ 取权重最大的那个域的
- **额外**算出 `night01`（见上）

刷新节流 **12Hz**（80ms）：每帧重新混一次会产生大量临时字典，
80ms 的间隔人眼看不出差别，GC 压力却小一个量级。

## 三、实体碰撞：树 / 楼 / 墙 / 栏杆都是实体

### 3.1 为什么不用 Godot 的物理系统

开放世界里是**几千栋楼 + 几千棵树 + 几十公里护栏**。
全部建成 `StaticBody3D` + trimesh 的话：

- 物理内存直接爆掉（trimesh 是逐三角形的）
- broadphase 每帧遍历上万碰撞体
- 而且车辆物理根本不走 Godot 物理引擎（是自写的运动学）

所以改成**自管一份简化碰撞体**：盒（建筑）+ 圆柱（树干 / 岩石 / 杆），
按 **120m 的空间哈希**分格。车辆每帧只查附近 3×3 格。

### 3.2 碰撞体登记

`OpenWorld.add_collider(pos, half, rot, y0, y1)`，其中 `rot` 是绕 Y 的偏航角。

登记点在 `OpenWorldScenery._place()` 里，按摆放 prefix 推断类别：

| prefix 含 | 类别 | 说明 |
|---|---|---|
| `block` `hero` `apt` `shed` `tower` `hut` `refinery` `lighthouse` `deck` | box | 建筑 / 高架护栏 |
| `palm` `pine` `dead` `burnt` `broad` | tree | 树干（圆柱） |
| `rock` `pole` `pipe` `barrel` | cyl | 岩石 / 管道 / 杆 |
| 其他 | 无 | 灌木、轮胎、浮标、栈桥、远船 |

用 prefix 推断而不是逐个调用点传参，是为了**新增摆点时不会忘记登记**。

登记时会用与 `RealAssetKit.place_chunked` **同一套**判据过滤
（`keepout_clear` + `true_radius`）：被道路禁入区丢掉的实例不登记，
否则会出现"看得见的楼没有碰撞体、看不见的楼反而挡路"。

### 3.3 车辆侧推出

`OpenWorld.push_out(x, z, radius, y)` —— 圆 vs 有向盒：

1. **粗筛**：碰撞体带外接半径 `rad`，先用平方距离排除掉绝大多数
2. **高度过滤**：只处理与车身高度有交集的障碍
3. **精确判定**：世界→局部→圆心到盒最近点→推出→局部→世界
4. 推出后**清掉速度的法线分量**：撞墙不穿墙，也不弹飞

**旋转的符号**是这一段最容易错的地方：

```
Basis(Vector3.UP, yaw).x = (cos(yaw), 0, -sin(yaw))
世界→局部:  lx = dx*cos - dz*sin,  lz = dx*sin + dz*cos
```

符号写反的后果不是"偏一点点"，而是**斜放的楼变成一堵堵错位的墙**，
车被推向莫名其妙的方向。本轮实测中该 bug 曾导致车被推出后仍留在楼体内部。

### 3.4 自检结果

```
[OW-TEST] colliders registered = 6483
[OW-TEST] embedded in building -> edge gap 1.45 m (must be >= 1.45)
[OW-TEST] OK  车身已被推出建筑体
[OW-TEST] ram building: dist 53.02 -> 53.13  speed=2.0
```

- 车塞进楼心 → 被推出到**正好 1.45m**（车身半径）外
- 40 m/s 撞向建筑 → 距离从 53.02 只变到 53.13，**一步都没穿过去**

## 四、车身陷进路面

### 4.1 根因

路面网格画在 `height_at(x, z) + 0.14`，而车辆贴地用的是 `height_at(x, z)`。
**两者差 14cm**，也就是轮子有三分之一陷在沥青里。

更糟的是：`is_on_road()` 用固定阈值 `road_distance <= 11`，
但路面实际半宽只有 6.5m（13m 宽的路）。**6.5~11m 的路肩被判成路面**——
那里物理给沥青抓地，视觉上却是野地起伏，车跟着土路走，直接陷进路肩。

### 4.2 修法

1. **路面抬升写进高度场**（`ROAD_LIFT = 0.10`）：
   `_splat_roads_into_heightfield` 把路面高程 + 10cm 直接写入高度场，
   于是「物理贴地高度」和「视觉路面高度」是**同一个数**，
   路面网格只再加 2cm 防 z-fighting。
2. **按格点记录路面半宽**（`road_half[]`）：
   `is_on_road()` 改成 `road_dist <= road_half + 0.6`，逐路精确判定。

### 4.3 实测

```
[OW-TEST] 路面采样点 = 9235   车体与路面最大高差 = 0.0200 m（应 < 0.05）
```

9235 个路面采样点，最大高差 2cm —— 轮子不再陷进路面。

## 五、清理场景中"奇奇怪怪的结构"

用户第一句话就是"里面有一些奇奇怪怪的结构 … 避免有穿模这种情况"。
这一节记录逐个排查出来的结构问题与根因。

### 5.1 坡道上的路被切成锯齿（最扎眼的一个）

**现象**：航拍图上，下坡的支路不是一条连续的沥青带，而是一串三角形的碎块，
白色（雪地 / 沙地）从两侧咬进路面，远看像拉链。

这一条挖出了**四个叠在一起的根因**，每个都得单独修，
修一个只能把戳穿深度降一个数量级。所以专门写了
`OpenWorld.probe_road_fit()` 来量化：沿路每 1m、横向取 7 个点，
量地形真实表面比路面高出多少（这就是"戳穿深度"）。

| 阶段 | 最深戳穿 | >0.05m | >0.2m | >0.5m | >1m |
|---|---|---|---|---|---|
| 修复前 | **18.93 m** | 10033 | 2549 | 704 | 202 |
| ① 线段投影 + 权重平均 | — | — | — | — | — |
| ② 压平区加宽 | 3.59 m | — | — | — | — |
| ③ 物理高度改三角面 | 2.32 m | 9569 | 2506 | 779 | 192 |
| ④ 路口高程迭代收敛 | 0.88 m | 6699 | 1297 | 164 | **0** |
| ⑤ 路面横向贴合地形 | **0.38 m** | **515** | **27** | **0** | **0** |

（样本共 273906 × 7 个横向采样点）

#### 根因一：路基高程取的是「最近采样点」的值，不是「折线上的插值」

路网采样点间隔 15m。原来 `_splat_roads_into_heightfield` 遍历每个采样点，
把周围格子往**这个点**的高程拉。落在两点之间的格子，高程是"某个端点的值"，
而路面网格却在两点之间拉了一条直线——坡道上这条直线会切进地形。

**修法**：改成按**线段**做投影：格子投影到最近的那一段折线上，
取投影点的插值高程 + `ROAD_LIFT`。
`u = clamp(dot(cell-a, ab)/|ab|², 0, 1)`，`ry = lerp(ys[i], ys[i+1], u)`。

#### 根因二：权重是顺序累加的，等于"覆盖"而不是"平均"

```gdscript
heights[idx] = lerp(heights[idx], target, w)   # 每处理一个采样点就推一次
```

`w` 接近 1 时这不是平均而是覆盖——最后处理的采样点独大，
整条路基跟着它走，坡道上相邻两点的路面高程就取错了。

**修法**：改成两遍。先累加 `wsum[idx] += w` 和 `ysum[idx] += w * ry`，
最后一次性 `heights[idx] = lerp(orig, ysum/wsum, clamp(wsum,0,1))`。
对称邻域下这个加权和**精确等于**中点高程。

#### 根因三：压平区不够宽，崖壁的顶点插进路面

高度场是 15.6m 一格。路的边坡只要有一个格子没压到，
崖壁的顶点就会插进路面里，把路顶出一块楔子。

**修法**：路缘外 **20m 内完全压平成路面高程**，再 30m 过渡回原地形。
（原来只铺 18m 且从路缘就开始衰减，崖壁没压住。）

#### 根因四：路口处两条路的高程不一致

环形主干道、放射支线、海岸环线、城内街道是**各自独立生成**的，
各自的平滑窗口位置不同——同一个路口上两条路能差出好几米。
压平时取平均，地形就被抬到两条路中间，**低的那条直接被地形埋掉**。

**修法**：迭代收敛。每一轮压平之后，从当前高度场重新读回每条路的高程
（`_refine_road_profiles()`），再压平。跑两轮之后所有路在路口收敛到同一个值。

#### 根因五：物理高度与画面地形不是同一个面

地形网格每个格被切成**两个三角形**，而 `height_at()` 原本是**双线性插值**，
两者在格内并不相等：

```
差值 = (h10 + h01 - h00 - h11) / 4
```

陡坡上实测能到 **1.4m**。以前车辆贴地、路面网格都取双线性值，
而画面上的地形是三角面——于是地形从路面下戳出来把路切成锯齿，
车也相对**可见地面**浮起来 / 陷下去（这正是用户说的"车陷进路面"）。

**修法**：`height_at()` 改成与 `_build_terrain_chunk` 的三角化**完全一致**的高度。
物理 = 画面 = 路面，三者永远一致。
法线 / 坡度仍走双线性版（`_height_bilinear`），否则坡度会一块一块地跳，
植被撒点会被整格整格地筛掉。

#### 配套：路面网格加密 + 横向贴合

- `_densify_road()` 把折线加密到 4m，每 4m 重新采一次地形高度；
- 横向取**三个点**（路缘 / 中线 / 路缘），各自按所在位置的地形高度取值：
  路是"贴"在地形上的，横向有坡度时整条横截面都跟着斜，
  否则上坡那一侧的路缘会被地形埋掉，只剩半条路。

#### 修完的效果

```
[OW-TEST] road fit: poke=0.377 m   >0.05/0.2/0.5/1.0/3.0 m : [515, 27, 0, 0, 0]
[OW-TEST] ground follow gap: -0.004 .. 0.000 m
```

车身贴地误差从 11mm 降到 **4mm**，路面再没有被地形戳穿超过 5cm 的地方
（只占全部采样的 0.03%）。

### 5.2 高架桥：从地面看只剩一排悬空的桥墩

**现象**：天际环城的高架快速路，桥面看不见，只剩几根柱子杵在半空。

**根因**：桥面是一张**零厚度**的平面，法线朝上。
从上面看是正面，从下面看就是背面 → 被背面剔除掉。

**修法**：`_build_deck_solid()` 做出顶面 / 底面 / 两侧立面，
桥面是有体积的实体，底面法线朝下，从地面仰视也看得见。

### 5.3 护栏悬在路中央，还在路中间凭空造墙

**现象**：桥面上方 1.2m 浮着一条横板，横跨整个桥面宽度。

**根因**：护栏的采样点全部落在桥面**中心线**上，只是抬高 1.2m，
然后用 `_build_deck_strip`（水平带状网格）画出来——于是是一块浮在路中央的横板。
更糟的是它也走了 `_build_deck_strip` 里的碰撞登记，
于是在路中间 ±0.8m 处凭空多出两堵看不见的墙。

**修法**：
- 护栏采样点压到桥面两侧边缘 `±(半宽 - 0.3)`；
- 改成 `_build_rail_strip()`：竖直护栏板 + 顶部横条（真实的护栏形状）；
- 碰撞体只在桥面两侧各登记一次。

### 5.4 缆车：只有塔，没有绳

**现象**：雪山域航拍能看到几座金属塔架，但塔与塔之间什么也没有。

**根因**：缆绳网格每个采样点只塞了 **1 个**顶点，
索引却按每点 2 个顶点算（`b = i*2`，取 `b` 和 `b+1`），
于是每个三角形都是"两个点重合"的**退化面**——面积恒为 0，什么都画不出来。

**修法**：按真实截面生成实体缆绳：每个采样点一个 4 顶点环
（左右各 0.11m、上下 0.20m），段与段之间接 4 个面。

顺带修了两处：

| 问题 | 原来 | 现在 |
|---|---|---|
| 缆绳弧度 | `+ sin(t*PI)*10`，缆绳往上鼓 | 塔间**下垂**（垂度按跨距给，最多 9m） |
| 缆绳与塔架 | 塔顶 = 地面+25，缆绳 ≈ 地面+26，对不上 | 塔高 30m，横担压在缆绳正下方 0.3m，绳真的搭在横担上 |

### 5.5 雪山域的"木屋"是一棵树

山间木屋摆的是 `realtree_broadleaf`——一棵树。
远看就是雪山上立着几棵特别大的树，是最扎眼的"奇怪结构"。
换成 `qt_house1` / `qt_house2`（真的房子模型）。

## 六、菜单切场景时的"两个世界叠加"
### 根因

`_clear_race()` 用 `race_root.queue_free()` 释放比赛场景。
**`queue_free` 要到帧末才真正删除**，这一帧里 `race_root` 还会照常渲染。
而同一帧里 `_show_menu()` 已经建好了菜单沙盘——于是画面上同时出现：

- 近处：菜单沙盘（辐射道路 + 8 组中英文标牌）
- 远处：2450m 外的真实雪山 / 熔岩地形

两者一起渲染，看起来像两个世界叠在一起。

### 修法

```gdscript
if race_root != null:
    # 立刻从场景树摘掉再 queue_free。
    if race_root.get_parent() != null:
        race_root.get_parent().remove_child(race_root)
    race_root.queue_free()
    race_root = null
```

`_free_menu_world()` 里的 `menu_world.queue_free()` 同理——
切换赛道时旧沙盘也会跟新沙盘叠一帧。

## 八、性能

| 阶段 | 耗时 |
|---|---|
| 高度场 + 路网 + 地形网格 | 9.8 s |
| 八域布景（楼 / 树 / 岩石 / 街灯 / 护栏） | 4.9 s |
| 其中：碰撞体登记 | 包含在布景内，零额外开销 |

世界构建从 5.7s 涨到 9.8s，多出来的 4.1s 花在两件事上：

1. **路口高程迭代**（压平 3 遍 + 重读剖面 2 遍，约 3s）：
   这是修"路在路口断成一截"的唯一办法，少一轮就会有一批路口对不齐。
2. **路面网格加密到 4m + 横向三点**（约 1s）：
   路面顶点数从 ~9.7 万涨到 ~55 万，换来路面严丝合缝地贴住地形。

如果加载时间需要压回来，优先砍迭代轮数（3 遍压平 → 2 遍），
其次把加密步长从 4m 放宽到 6m——这两项都会让路面重新出现零点几米的缺口。

域色渐变让地形构建从 4.5s 涨到 5.6s（+25%），
这是 33 万个顶点各算 9 次域权重的代价；
初版每顶点建一个 dict 数组，直接翻到 1.5 倍，已改为零分配实现。

碰撞查询每帧 3×3 格，粗筛后真正做精确判定的只有个位数。

## 九、第三轮视觉复核：楼骑在路上、熔岩平板、雪山刷白

第一轮修完路面与碰撞后，逐域截图复核又挖出三类"结构"问题，
根因都不在上一轮改的地方，而在**布景层的尺度与净空判据**。

### 9.1 净空判据只看「楼心」，不看「楼体」

原来的判据是 `road_distance_at(p) < 26.0 → 跳过`，
即"楼的**中心点**离路中心线够远"。但一栋 88m 宽的楼，
中心离路 30m，楼身照样压在路面上——天际环城那面贴满画面的砖墙就是这么来的。

**修法**（三层）：

| 层 | 改动 | 说明 |
|---|---|---|
| 判据 | `road_edge_distance_exact(p) >= 楼体占位半径 + 3.5m` | 判的是**楼体外边缘**离**路面边缘**的距离 |
| 半径 | `RealAssetKit.footprint_radius(asset, scale)` | 缩放后 XZ 包围盒对角线的一半（楼随机偏航摆，外接圆最保险） |
| 尺度 | `RealAssetKit.scale_for_height_capped(asset, h, max_footprint)` | 按目标高度反推倍率后，再被"占位半径上限"截断 |

**为什么不用现成的 `road_distance_at`**：那张表是按 15.6m 高度场格点存的距离场，
查询点离格点最远差 11m，而净空容差只有几米——直接拿来判会有三成概率判错。
新增 `OpenWorld._build_road_index()` + `road_edge_distance_exact()`：
把路网折线拆成线段塞进 64m 空间哈希（键用 `Vector2i`），查询时做点-线段投影，
拿到真正的"到路面边缘的距离"，误差 < 1m。

**为什么还要压住尺度**：净空判据改成"楼体外边缘"之后，楼体就必须真的塞不进路里。
城内街道的间距只有 62m（`block=124` + 奇偶行错开 62m），
一条走廊里放不下 88m 宽的楼——只能让楼变小：

| 资产 | 天然尺寸 (x,y,z) | 天然占位半径 | 原目标高度 | 现目标高度 | 现实际高度 |
|---|---|---|---|---|---|
| `downtown_large` | 20.6 × 28.0 × 16.6 | 13.3m | 78~92m | 40~46m | 32~44m |
| `downtown_medium` | 15.1 × 25.0 × 13.1 | 10.0m | 44~52m | 30~34m | 30~34m |
| `colony_tower` | 16.0 × **91.3** × 15.5 | 11.2m | 176m | 176m | 176m |
| `station_tower` | 15.0 × 42.3 × 16.0 | 11.0m | 152m | 58~152m | 受占位上限约束 |

**高层交给天然纤细的塔**：`colony_tower` 天然就是 91m 高、16m 宽的细高塔，
放大到 176m 依然是塔；`downtown_large` 天然只有 28m 高、20m 宽，
放到 92m 就是一堵摊开的墙。

### 9.2 三个"躺平"的资产被当成塔/楼

用 `tools/probe_glb_nodes.py`（解析 GLB 节点 TRS + 四元数）逐个查了塔类资产：

|---|---|---|---|
| `lovedeath_tower` | **LoveDeath_Tower_Bridge_Art** | 是**桥**，62m 长 × 31m 高 | 从楼池移出，改到港湾当跨海桥 |

### 9.3 熔岩域的巨型橙色平板 / 冰川域的悬浮白板

`_build_magma()` 原来撒 70 块 `_glow_boxes`：单块最大 **46 × 0.5 × 30m** 的
`BoxMesh` + UNSHADED 自发光，中心按地形高度 `+0.45` 摆（盒子横跨 h+0.20 ~ h+0.70）。
落到坡上就是一半悬空一半埋地的橙色平行四边形，航拍下去满坡散着"扑克牌"，
车开进去还会被整块盖住。

`_build_glacier()` 的 `IceSheet` 同理：18~52m 的大方板固定摆在 `LAKE_LEVEL-0.2`，
湖岸斜坡处整块翘出来。

**修法**：新增贴地薄片生成器（`_patch_add` / `_patch_build` / `_downhill`），
每个顶点按 `world.height_at()` 取当地地形高度，生成真正贴地的网格：

- 熔岩：90 段细长熔岩带（9~20m × 3.5~7.5m），**顺着坡往下淌**
  （朝向取地形梯度的下坡方向），避开路面 9m 以上；
- 冰层：44 片浮冰（7~17m），逐顶点贴地且高度被湖面 `LAKE_LEVEL` 压住；
- 火山口：7 个贴地熔岩口。

### 9.4 熔岩域的地表被刷成雪白色

地面探针（`tools/ow_ground_color.gd`）实测：熔岩域中心的顶点色是
**(0.764, 0.799, 0.857)** —— 冰川的雪色。

根因：`_ground_color()` 里"主导域权重不足 90% 就退化成中性野地（wild）"
这个判定，用的是**颜色权重**（半径 2.6 倍域半径，为的是长渐变）。
但隔着 1.8km 的冰川会把 **39%** 的颜色权重渗进熔岩域中心，
于是"过渡带"条件在**域中心**也成立 → `kind` 变成 `wild` →
套上"过渡带 = 中性野地"的雪线规则 → 火山顶被刷成雪白。

**修法**：把"特效类别"和"基色"拆成两套判定。

- 基色：继续用颜色权重（2.6 倍半径）做长渐变 —— 这是用户要的效果；
- 特效（雪线 / 岩层 / 陡坡露岩）：改用**地形权重**（1.55 倍半径）判定，
  新增 `kind_ids`（每格一个类别）+ `_effect_kind()`。

地形权重才是"这块地貌属于谁"的答案：域中心永远 100% 主导，
只有真正的过渡带才退化成中性野地。修完熔岩域中心顶点色 = **(0.160, 0.109, 0.099)**（深色火山岩），
城区配色一字未变。

### 9.5 开放世界 HUD 整个塌在屏幕左上角

> ⚠️ 本节记录的是**第三轮**的临时修复：当时开放世界有一套独立的 `OpenWorldHUD`。
> 第四轮已按用户要求把这套独立 HUD 整体退场，开放世界改用赛道同一套 `RaceHUD`，
> 详见第十节。`scripts/openworld/open_world_hud.gd` 已删除。

`OpenWorldHUD extends Control`，直接挂在 `Main`（Node3D）下。
Control 的锚点是相对**父矩形**解析的，而父矩形只有在父节点是 CanvasItem 时才有值——
挂在 Node3D 下时父矩形是 0×0，于是整个 HUD（区域横幅 / 速度表 / 小地图 / 遥测）
全部塌在屏幕左上角被裁掉，区域横幅只剩半截字。

同项目的 `Menu` 和 `RaceHUD` 都是 `extends CanvasLayer`，所以它们正常。

**修法**：`OpenWorldHUD` 改成 `extends CanvasLayer`（`layer = 4`），
去掉 `set_anchors_preset` 与 `mouse_filter`，并删掉 `main.gd` 里对它的
`queue_redraw()` 调用（CanvasLayer 不是 CanvasItem，没有这个方法）。
顺带修了一个文案错位：区域切换时横幅弹出期间，常驻行显示的还是**上一个域**的名字
（会出现"冰川湖"下面挂着"NEON CITY"），现在切换时同步更新；
常驻行内容与横幅重复，改成横幅在场时隐藏、随横幅淡出交叉淡入。

## 十、第四轮：进开放世界看到的是菜单沙盘 + HUD 两套并存的合并

### 10.1 用户诉求（原话）

> 这个开放世界其实也属于一个赛道，就是里面所有界面内容跟那个呃咱们正常的前八个那个赛道是一样的，
> 只有这个右上角这个地图啊，你这个做的很好可以保留。
> 然后呢底下的 HUD 那个时速表那些信息都跟那些保持一致就可以。不用单独做成这样。

拆成两件事：

1. **进开放世界后看到的不是驾驶视角，而是菜单里那张俯视沙盘**；
2. **开放世界有一套自己的 HUD**（左下独立速度表 + 右下独立遥测 + 顶部区域横幅），
   和前八条赛道的 `RaceHUD` 是两套完全不同的界面。

### 10.2 沙盘俯视的两个根因

截图放大后，3D 画面里能逐项对上 `_build_open_world_showroom()` 的产物：
300m 半径大陆圆盘、8 条辐射支线、8 座微缩区域城、中英双行 Label3D 域标牌、中央枢纽塔。
所以问题不是"渲染错了"，而是**菜单沙盘根本没有被拆掉**。

**根因 A：`_start_race()` 的开放世界分支提前 return。**

```gdscript
if bool(track_def.get("openWorld", false)):
    _start_open_world(current_track_id, current_car_id, mode)
    return          # ← 在 _free_menu_world() 之前就返回了
...
_free_menu_world()   # ← 常规赛道走这里，开放世界永远走不到
```

沙盘世界（`menu_world`）和它的相机（`menu_cam.current = true`）一路留到了开放世界里。

**根因 B：新的追尾相机没有接管。**

`Camera3D` 后加入场景树时**不会**自动成为 current，只有当原有 current 相机被释放后
Godot 才会把 current 提升给另一台相机。探针实测：

```
[PROBE] A added, A.current = true
[PROBE] B added (no explicit current)
[PROBE]   A.current = true
[PROBE]   B.current = false
[PROBE] viewport.get_camera_3d() = <Object#null>
[PROBE] after freeing A:
[PROBE]   B.current = true
```

修法：

```gdscript
# _start_race()
if bool(track_def.get("openWorld", false)):
    _free_menu_world()          # 菜单沙盘必须先拆掉
    _start_open_world(current_track_id, current_car_id, mode)
    return

# _start_open_world()
cam.follow(car, null)
cam.world = open_world
cam.current = true              # 相机接管必须显式指定
```

### 10.3 HUD 合并：RaceHUD 增加开放世界模式

**结论：开放世界不再有自己的 HUD 类，直接用 `RaceHUD`。**
`scripts/openworld/open_world_hud.gd` 整体删除，`main.gd` 里的 `open_world_hud`
字段与 `_clear_race()` 中的释放分支一并移除。

用户明确要保留的只有**右上角那张全域图**，其余全部走赛道那一套：

| 位置 | 前八条赛道 | 开放世界（合并后） |
|---|---|---|
| 左上信息牌 | 赛道名 / 模式 / 相机 / FPS | `无界大陆 CONTINENT` / `自由漫游 FREE ROAM · 9 × 9 km` |
| 左上计时条 | 总时间 / LAP / 本圈·上圈·最佳 | 总时间 / **当前区域** / 海拔·地表·里程 |
| 顶部正中 | 赛段小地图（`_map_panel`） | **隐藏**（开放世界没有赛道可画） |
| 右上 | 名次牌 P4 | **全域图**（`ContinentMap`），名次牌隐藏（没有对手） |
| 右下仪表卡 | 转速环 + 速度 + 档位 + 油门刹车 + 氮气 | **完全相同**，同一段 `_refresh_cluster()` |
| 底部提示行 | 操作键位 | **完全相同** |
| 中央提示 | 倒计时 / 超车 / 尾流 / 最终圈 | 区域切换时借 `toast_label` 报一次域名 |

代码上做了三件事：

1. **`RaceHUD.refresh()` 拆出 `_refresh_cluster()` / `_refresh_common()`**，
   赛道与开放世界共用仪表卡和提示行；
2. **`RaceHUD.bind_open_world()` / `refresh_open_world()`**：
   `rm` 为 `null` 时按"一直在跑"处理（`_update_shift_lights`、`_update_nitro`
   原来都写死 `rm.state == RACING`），倒计时 / 尾流 / 超车 toast 这些
   依赖 `RaceManager` 的逻辑在开放世界里直接跳过；
3. **全域图抽成 `RaceHUD` 的内类 `ContinentMap`**：
   沿用原来的 256×256 一次性烘焙（大陆轮廓 + 108 条路网），
   运行时只叠一个玩家箭头 + 一根 1 km 比例尺。
   箭头这次改成**跟着车头方向转**（地图 x → 世界 x，地图 y → 世界 z，
   旋转角 = `heading - π`），原来的箭头永远朝上，车一拐弯就指错了方向。

### 10.4 顺带修掉的相机穿帮

全量回归里 `[M3] chase camera clips outside guardrail` 这条没过：
`_keep_camera_on_track()` 用指数逼近把镜头拉回护栏内，
一帧只拉回 12%~35%，要 5~8 帧才收敛 —— 这几帧镜头停在护栏外面，
观众会直接看到护栏另一侧的景物。改成**硬夹**到走廊边界
（`half_width + 1.1`），实测 `camera clamp: lateral=9.60m`（限值 9.80m）。

### 10.5 端到端验收工具
